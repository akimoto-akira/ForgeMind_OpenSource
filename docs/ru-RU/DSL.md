# ForgeMind DSL (Domain-Specific Language)

> Этот документ объясняет, что такое ForgeMind DSL, как он работает и какую роль играет в общей системе. Предназначен для разработчиков, которые хотят понять или использовать ForgeMind DSL.

---

## 1. Что такое DSL

**DSL (Domain-Specific Language)** — это **декларативный кодовый канал** в ForgeMind для массового создания или изменения ресурсов игрового движка с помощью ИИ.

Он позволяет ИИ использовать читаемый текст в стиле синтаксиса C# для описания создаваемых или изменяемых ресурсов (таких как Blueprints, Materialы, Behavior Trees и т.д.), затем переводить их в структурированное IR (Intermediate Representation) с помощью переводчиков и отправлять в редактор движка для применения.

### 1.1 Основная модель

Ключ к пониманию ForgeMind DSL — следующий pipepline:

```
ИИ
  ↓  выводит строку DSL
DSL
  ↓  переводится переводчиком
IR (Промежуточное представление)
  ↓  передается через Bridge
Companion (адаптер движка)
  ↓  применяется
Ресурс движка
```

Этот pipeline делится на две фазы:

- **Фаза перевода** (на стороне сервера MCP): Текст DSL переводится в IR JSON парсером. Переводчик выполняет только синтаксический анализ; он не компилирует, не разрешает внешние ссылки, не обращается к диску. Любая ошибка перевода прерывает всю пачку, и IR не отправляется в движок.
- **Фаза применения** (на стороне движка): Companion получает IR JSON и применяет операции создания/обновления/удаления ресурс за ресурсом. Отказ одного ресурса не влияет на другие ресурсы в той же пачке.

### 1.2 Связь между DSL и MCP Action

Возможности управления ИИ в ForgeMind происходят из двух типов инструментов:

| Измерение | MCP Action | DSL |
|-----------|-----------|-----|
| Гранулярность | Точечный контроль одной сущности | Массовое декларативное создание/изменение |
| Пример | Добавить переменную, соединить провод | Блок текста, создающий весь ресурс Blueprint |
| Канал | Отправлен напрямую в движок через Bridge | Сначала переведен в IR, затем отправлен через Bridge |
| Роль | Точная настройка | Архитектурное проектирование |

Оба являются **дополнительными** — DSL отвечает за массовое строительство «с нуля», в то время как Action отвечает за точную настройку «от хорошего к отличному».

## 2. Где DSL находится в системе

```
┌──────────────┐   MCP   ┌──────────────────────────┐
│  Клиент ИИ    │ ◄────► │  ForgeMindServer (хост)   │
└──────────────┘         │  • Получает строку DSL      │
                         │  • Вызывает переводчик      │
                         │    для создания IR          │
                         │  • Отправляет IR через Bridge│
                         └────────────┬─────────────┘
                                      │ локальный TCP-мост
                         ┌────────────▼─────────────┐
                         │  Companion (адаптер движ.)│
                         │  • Получает IR            │
                         │  • Применяет по ресурсу   │
                         │  • Компилирует / Сохраняет │
                         └──────────────────────────┘
```

Позиция DSL в ForgeMind:
- ИИ выводит текст объявления DSL
- Инструмент MCP `dsl` получает текст и вызывает переводчик для создания IR JSON
- IR JSON отправляется в редактор живого движка через TCP Bridge
- Companion (адаптер движка) применяет его в редакторе для завершения генерации ресурсов

## 3. Базовый синтаксический стиль DSL

DSL заимствует синтаксическую форму C#, но **не проходит через компилятор C#**. Он имитирует соглашения о написании C#, но управляет внутренним семантическим анализом компилятора (проверка типов, разрешение перегрузки и т.д.) внутри самого переводчика.

### 3.1 Структура блока объявления

Каждый блок объявления DSL — это объявление класса верхнего уровня (или struct/enum) с `[Attribute]`:

```csharp
[DomainAttr(Path = "/Game/Path/ResourceName", Mode = Create)]
[AdditionalAttributes]
public class ResourceName
{
    // объявления членов: переменные, компоненты, функции и т.д.
}
```

### 3.2 Режимы Create / Update / Delete

Все домены равномерно поддерживают три режима работы:

| Значение режима | Значение | Полезная нагрузка |
|-----------------|----------|-------------------|
| `Create` | Создать новый ресурс | `definition` (полное определение ресурса) |
| `Update` | Изменить существующий ресурс | `patches` (массив целевого состояния по членам) |
| `Delete` | Удалить весь ресурс | пустой `patches` |

**Пример Create:**
```csharp
[Blueprint(Path = "/Game/Blueprints/BP_Chest", Mode = Create)]
[Extends(typeof(Actor))]
public class BP_Chest
{
    [Variable] float Health = 100f;
}
```

**Пример Update:**
```csharp
[Blueprint(Path = "/Game/Blueprints/BP_Chest", Mode = Update)]
public class BP_Chest
{
    [Variable] float MaxHealth = 200f;     // нет в ресурсе → добавить
    [Variable(Category = "Stats")]
    float Health = 90f;                    // уже в ресурсе → заменить
    [Delete]                              // пометить для удаления
    float LegacyVariable;                  // → удалить существующий член
}
```

Фактический тип операции (add / replace / delete) выводится Companion на основе наличия члена в целевом ресурсе и наличия аннотации `[Delete]` — а не объявлен явно в DSL.

**Пример Delete:**
```csharp
[Blueprint(Path = "/Game/Blueprints/BP_OBSOLETE", Delete = true)]
public class BP_OBSOLETE { }
```

### 3.3 Ссылка на другие ресурсы — псевдонимы using

DSL поддерживает синтаксис псевдонимов `using` для упрощения ссылок между ресурсами:

```csharp
// using на уровне файла (применяется ко всем блокам)
using WoodTex = "/Game/Textures/T_Wood.uasset";

// using на уровне блока (применяется только к этому блоку)
[Blueprint(Path = "/Game/Chest/BP_GoldenChest", Mode = Create)]
public class BP_GoldenChest
{
    using GoldMat = "/Game/Materials/M_Gold.uasset";
    [Variable] MaterialInstance Mat = MaterialInstance(GoldMat);
}
```

Это синтаксическое соглашение DSL — `using` сопоставляет идентификаторы со строками пути ресурсов для удобства ссылок в объявлениях.

### 3.4 Межблочные ссылки на типы

В дополнение к явному `using`, DSL также поддерживает неявные межблочные ссылки на типы:

Если объявление верхнего уровня — `[Blueprint(Path="/Game/AI/BP_Hunter")] public class BP_Hunter { ... }`, идентификатор `BP_Hunter` можно использовать непосредственно в последующих блоках, и он автоматически разрешается в путь ресурса `"/Game/AI/BP_Hunter"`.

### 3.5 Комментарии

DSL поддерживает комментарии в стиле C#:
- `//` однострочные комментарии
- `/* */` блочные комментарии

Комментарии не производят вывод IR.

## 4. IR (Промежуточное представление)

IR — это промежуточный продукт перевода между переводчиком и Companion — структурированное описание ресурса в формате JSON. Это «мостовой язык» между DSL и движком.

### 4.1 Batch IR vs. IR одного ресурса

**Batch IR** (мульти-ресурсная пачка):
```json
{
  "version": "5.6",
  "batch": true,
  "assets": [
    { "assetType": "blueprint", "path": "/Game/BP_A", "mode": "create", ... },
    { "assetType": "material",  "path": "/Game/M_Wood", "mode": "create", ... }
  ]
}
```

**IR одного ресурса**:
```json
{
  "version": "5.6",
  "assetType": "blueprint",
  "path": "/Game/Blueprints/BP_Chest",
  "mode": "create",
  "compile": true,
  "save": false,
  "definition": { ... }
}
```

### 4.2 Справочник полей IR одного ресурса

| Поле | Тип | Описание |
|------|-----|----------|
| `version` | string | Версия движка (например, `"5.6"`), должна точно соответствовать основной версии |
| `assetType` | string | Тип домена (определяется Attribute блока) |
| `path` | string | Путь ресурса (обязательно) |
| `mode` | string | `create` / `update` / `delete` |
| `compile` | bool | Компилировать после применения (по умолчанию true) |
| `save` | bool | Сохранить на диск после применения |
| `patches` | array | Обязательно для режима update (целевое состояние по членам, без поля op) |
| `definition` | object | Обязательно для режима create (полное определение ресурса) |

> **Ограничение режима/нагрузки**: `mode=create` должен нести `definition` и не должен включать `patches`; `mode=update` должен нести `patches` и не должен включать `definition`; `mode=delete` несёт пустой `patches`. Любое несоответствие — недопустимая нагрузка.

### 4.3 Двунаправленная симметрия

IR ForgeMind использует **одинаковую структуру полезной нагрузки** как в «направлении записи» (`apply_asset_ir`), так и в «направлении чтения» (`get_asset_ir`):

| Направление | Команда | Значение `mode` |
|-------------|---------|-----------------|
| Запись | `apply_asset_ir` | `create` / `update` / `delete` |
| Чтение | `get_asset_ir` | `read` |

Это позволяет ИИ «читать → изменять mode → записывать обратно» ту же IR без преобразования схемы.

## 5. Распознавание и маршрутизация доменов

### 5.1 Attributes определяют домены

Каждый блок объявления в строке DSL автоматически маршрутизируется к своему типу ресурса через его маркер `[Attribute]`:

```csharp
[Blueprint(Path = "...")]          // → переводчик Blueprint → assetType = "blueprint"
[Material(Path = "...")]           // → переводчик Material  → assetType = "material"
[BehaviorTree(Path = "...")]       // → переводчик Behavior Tree → assetType = "behavior_tree"
```

**Таблица сопоставления Attribute → assetType:**

| Attribute | Тип ресурса |
|-----------|-------------|
| `[Blueprint]` | `blueprint` |
| `[WidgetBlueprint]` | `widget_blueprint` |
| `[Material]` | `material` / `material_instance_constant` |
| `[MaterialFunction]` | `material_function` |
| `[BehaviorTree]` | `behavior_tree` |
| `[Blackboard]` | `blackboard` |
| `[AnimBlueprint]` | `anim_blueprint` |
| `[Enum]` | `user_defined_enum` |
| `[Struct]` | `user_defined_struct` |
| `[InputAction]` | `input_action` |
| `[InputMappingContext]` | `input_mapping_context` |
| `[NiagaraEmitter]` | `niagara_emitter` |
| `[NiagaraSystem]` | `niagara_system` |
| `[MetaSoundSource]` | `meta_sound_source` |
| `[ChaosSolver]` | `chaos_solver_actor` |
| `[GroomBinding]` | `groom_binding_asset` |
| `[Landscape]` | `landscape` |
| `[FoliageType]` | `foliage_type` |
| `[PhysicsAsset]` | `physics_asset` |
| `[PaperFlipbook]` | `paper_flipbook` |
| `[LevelSequence]` | `level_sequence` |
| … | … |

> В таблице выше отображены все известные на данный момент домены. Для добавления нового домена требуется только зарегистрировать новое сопоставление Attribute → переводчик на стороне перевода — хост-фреймворк не нуждается в изменениях.

### 5.2 Правила маршрутизации

- Парсер выполняет точное совпадение имени для каждого блока объявления (на уровне токенов, а не подстрок)
- При наличии нескольких Attributes первым считается первый в таблице сопоставления (`[WidgetBlueprint]` приоритетнее `[Blueprint]`)
- **Нераспознанный Attribute не откатывается без уведомления** — он сообщает об ошибке и прерывает всю пачку

### 5.3 Смешивание нескольких доменов в одном DSL

Одна строка DSL может содержать **любое количество блоков объявлений любого домена**:

```csharp
using WoodTex = "/Game/Textures/T_Wood.uasset";

// ── Блок 1: домен Blueprint ──
[Blueprint(Path = "/Game/AI/BP_Hunter", Mode = Create)]
[Extends(typeof(Actor))]
public class BP_Hunter
{
    [Variable(Category = "Stats")]
    float Health = 100f;
}

// ── Блок 2: домен Behavior Tree ──
[BehaviorTree(Path = "/Game/AI/BT_Hunter", Mode = Create)]
public class BT_Hunter { }

// ── Блок 3: домен Material ──
[Material(Path = "/Game/Materials/M_Wood", Mode = Create)]
public function M_Wood
{
    BaseColor = Texture2D(WoodTex);
    Roughness = 0.7f;
}
```

Все блоки объявлений в одном DSL переводятся независимо, каждый производит свою собственную IR, собираемые в один Batch IR и отправляемые в движок вместе через Bridge.

## 6. Bridge и Companion

### 6.1 Транспорт Bridge

IR отправляется в редактор движка через локальный TCP-мост:
- Слой моста отвечает за надежную доставку IR на сторону движка
- Bridge — это инфраструктура локальной межпроцессной связи ForgeMind: хост-сторона управляет сервером моста, сторона адаптера движка управляет клиентом моста

### 6.2 Обязанности Companion

Companion — это плагин адаптера внутри движка (например, ForgeMindForUE). Его обязанности включают:

1. **Получить IR JSON** → направить обработчику домена движка на основе `assetType`
2. **Create**: Построить полный ресурс из `definition` → зарегистрировать в реестре ресурсов → необязательно компилировать → необязательно сохранить на диск
3. **Update**: Применить изменения на уровне членов из `patches` (add / replace / delete выводится Companion)
4. **Delete**: Выгрузить пакет ресурса → удалить из реестра ресурсов → удалить файлы на диске
5. **Отчет о результатах**: Вернуть успех / ошибку для каждого ресурса; направление записи возвращает `patchResults[].actualOp`

> Отказ одного ресурса не влияет на другие ресурсы в той же пачке (без отката транзакций). Это сознательный выбор дизайна в ForgeMind — пространство состояний ресурсов редактирования велико, стоимость транзакций высока, и частичный успех предпочтительнее «всё или ничего».

## 7. Диагностика и обработка ошибок

Обработка ошибок DSL делится на две фазы:

| Фаза | Типы ошибок | Обработка |
|------|------------|-----------|
| Фаза перевода (сторона MCP) | Синтаксические ошибки, нераспознанные Attributes, отсутствующие обязательные параметры и т.д. | Любая ошибка → пачка прервана, IR не отправлен в Bridge |
| Фаза применения (сторона Companion) | Ресурс не найден, тип не совпадает, сбой компиляции и т.д. | Отказ одного ресурса не влияет на другие ресурсы пачки |

Предупреждения (Warn) во время фазы перевода не прерывают пачку, но прикрепляются к тексту ответа, возвращаемому ИИ.

### 7.1 Общие коды ошибок фазы перевода

Некоторые примеры кодов ошибок (обратитесь к документации домена для деталей):

| Код ошибки | Значение |
|-----------|----------|
| `FM1004` | Недопустимое значение Mode |
| `FM1005` | Отсутствует обязательный параметр Path |
| `FM1002` | Сбой перевода домена (общий код отката) |

### 7.2 Основные коды ошибок уровня ресурсов (фаза применения)

| Код ошибки | Значение |
|-----------|----------|
| `ASSET_NOT_FOUND` | Путь ресурса не существует (сценарии update / delete) |
| `ASSET_ALREADY_EXISTS` | Путь уже существует (сценарий create, без перезаписи по умолчанию) |
| `ASSET_TYPE_MISMATCH` | Тип не соответствует |
| `ASSET_LOCKED` | Ресурс заблокирован в редакторе |

## 8. Расширение доменов DSL

### 8.1 Компоненты домена

Полный домен DSL состоит из следующих компонентов:

1. **Маркер Attribute** — например, `[Blueprint]`, `[Material]`, используется для распознавания маршрутизации
2. **Реализация переводчика домена** — отвечает за перевод объявлений DSL этого домена в IR JSON
3. **Документация синтаксиса DSL** — определяет правила объявления и параметры Attribute для домена
4. **Соглашение схемы IR** — определяет JSON-структуру `definition` / `patches` домена
5. **Обработчик домена Companion** — соответствующая реализация на стороне движка, применяющая ресурсы из IR в редакторе

### 8.2 Основные шаги для добавления нового домена

1. Определить имя корневого Attribute домена (например, `[NewDomain]`)
2. Реализовать переводчик домена (наследовать базовый класс переводчика, переопределить методы посетителя синтаксического дерева для извлечения семантики домена, выдать IR JSON)
3. Зарегистрироваться в фреймворке, чтобы парсер мог найти переводчик через `assetType`
4. Написать документацию синтаксиса DSL и соглашения схемы IR
5. Реализовать соответствующий обработчик домена на стороне Companion движка

Добавление нового домена **не требует изменений в коде хоста** — фреймворк обнаруживает новые переводчики доменов через механизм регистрации.

### 8.3 Принципы реализации переводчиков

Переводчики следуют следующим контрактам поведения, которым нужно следовать при расширении доменов DSL:

- **Чистая функция**: Переводчик принимает строку DSL в качестве ввода и выдает IR JSON в качестве вывода, без побочных эффектов и без остаточного состояния. Один и тот же DSL всегда выдает одну и ту же IR.
- **Только синтаксический анализ**: Переводчики не выполняют компиляцию C#, не обращаются к диску, не разрешают внешние активы; они только переводят синтаксическую форму DSL в IR. Семантическая проверка — ответственность стороны движка.
- **Восстановление после ошибок**: Может терпеть нестандартный синтаксис DSL (например, присваивание строки псевдонимам `using`) без прерывания перевода.
- **Деградация неизвестного синтаксиса**: При встрече синтаксиса, который не может быть переведен точно, сообщает предупреждение вместо ошибки, оставляя его фазе применения движка.

## 9. Граница Open Source и Commercial

Возможности DSL ForgeMind делятся на две части:

### 9.1 Open Source (Открытое ядро)

Открытое ядро предоставляет хост-фреймворк DSL:

- **Уровень фреймворка DSL**: Отвечает за разбор строк DSL (разделение по блокам объявлений верхнего уровня, распознавание Attributes и маршрутизация к переводчикам), интерфейсы переводчиков и механизмы регистрации, диагностические отчеты и другую инфраструктуру.
- **Контракт плагина и механизм регистрации**: Новые переводчики доменов обнаруживаются через регистрацию; хост-фреймворк не нуждается во встроенной логике ветвления доменов.
- **Open Source исключает переводчиков доменов**: Конкретная логика перевода доменов (Blueprints, Materials, Behavior Trees и т.д.) не входит в открытое ядро.

### 9.2 Commercial (Платное расширение)

Модуль коммерческого расширения основывается на открытом фреймворке для предоставления:

- Все реализации конкретных переводчиков доменов (Blueprint, Material, Behavior Tree, AnimBlueprint, Niagara, MetaSound, Chaos, Groom, Landscape, Foliage, Physics, Paper2D, Sequencer, …)
- Точка входа инструмента MCP `dsl`, служащая точкой выполнения для перевода и отправки DSL
- Конвертеры IR по доменам, выполняющие обработку, специфичную для домена, перед отправкой IR в движок

> Открытое ядро определяет фреймворк и механизм расширения; конкретные возможности доменов (синтаксис DSL и переводчики для Blueprints, Materials, Behavior Trees и т.д.) предоставляются модулем коммерческого расширения. Пользователи открытого ядра могут регистрировать собственные переводчики доменов на основе фреймворка для расширения своих возможностей DSL.

## 10. Поведенческие ограничения и принципы дизайна

| Тег | Поведение DSL | Значение |
|-----|-------------|----------|
| Синтаксический стиль | Вдохновлен C# | C# — язык с наибольшим объемом обучающих данных ИИ, снижая когнитивную нагрузку |
| Координаты узлов | Не выражены в DSL | Касается только «что существует и как они связаны» — топологическая семантика; макет генерируется движком автоматически |
| Path обязателен | Да | Соглашения по именованию и принадлежность модуля явно определяются ИИ |
| Совпадение версий | Точная основная версия | `version` IR должна соответствовать основной версии движка |
| Политика транзакций | Без отката | Частичный отказ ресурса в пачке не влияет на другие ресурсы |
| Тестовый прогон | Не существует | IR только отправляется в движок и не возвращается вызывающему |
| Нераспознанный Attribute | Прерывает пачку | Тихий откат привел бы к тому, что ИИ по неосторожности создал бы неверный тип ресурса |
| Update patch | Выражает целевое состояние | Patch не несет поля `op`; операции выводятся Companion на основе наличия члена |

## 11. Краткий справочник

### Шаблон блока объявления DSL

```csharp
using SomeAsset = "/Game/Path/SomeAsset.uasset";

[DomainAttr(Path = "/Game/Path/YourAsset", Mode = Create)]
[AdditionalAttribute]
public class YourAsset
{
    using BlockAlias = "/Game/Path/AnotherAsset.uasset";
    [Variable] float YourVariable = 1f;
    [Function(Pure = true)]
    bool YourFunction() => YourVariable > 0;
}
```

### Шаблон IR одного ресурса

```json
{
  "version": "<major.minor>",
  "assetType": "<snake_case_type>",
  "path": "/Game/Path/Asset",
  "mode": "create",
  "compile": true,
  "save": false,
  "definition": { }
}
```

### Обзор pipeline

```
Клиент ИИ
  → DSL (текст, содержащий один или несколько блоков объявлений домена)
  → Инструмент MCP dsl (фаза перевода)
    → парсер маршрутизирует к переводчику домена на основе Attribute
    → переводчики производят IR JSON
  → Batch IR ({ version, batch, assets })
  → Bridge (локальный TCP)
  → Companion (фаза применения)
    → Создать / Обновить / Удалить / Компилировать / Сохранить по ресурсу
  → Ресурс движка
```
